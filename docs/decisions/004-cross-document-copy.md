# 004. 문서 사이 문단·표 복사: importParagraphBlock + 번호·스타일 보정

## 상황

SPEC-007(여러 문서와 문서 사이 복사)의 `copy_blocks` 에 들어가기 전에, `@rhwp/core` 0.8.7 공개 API 로 다른 문서의 문단·표를 서식째 가져올 수 있는지 확인해야 했다(#62, 스펙 열린 질문 "문서 사이 복사가 rhwp 공개 API 로 서식째 되는지").

- 문서는 탭마다 따로 있으므로, 원본 탭이 원본을 **HWPX 바이트**로 내보내고 대상 탭이 그 바이트를 새 핸들로 열어 `importParagraphBlock(source, options)` 하는 순서(스펙 기술 메모)
- 가져올 것: 보통 문단, 자동 번호 문단, 개요 문단, 표, 그림이 든 문단, 스타일을 쓴 문단(대상에 있는 이름 / 없는 이름), 누름틀 문단
- 글자 모양·문단 모양·스타일·번호가 유지되는지, HWPX 로 저장해 다시 열어도 같은지
- **대상에 없는 스타일·모양 id** 가 어떻게 되는지(원본 id 를 그대로 쓰면 대상의 엉뚱한 정의를 가리킨다)
- 안 되면 `exportSelectionHtml` → `pasteHtml` 대안과 비교

확인은 프로토타입 함수(`src/core/copy-paragraphs.ts` `copyParagraphs`)와 테스트(`tests/copy-spike.test.ts`, 묶음 `SPEC-007 문서 사이 복사 … (기술 검증)`, 원본 문서 `tests/copy-source.ts` = 공문 fixture + 그림 문단·"강조 문단" 스타일 문단·"개요 1" 스타일 문단), 한글 확인 파일 생성 스크립트(`scripts/make-copy-check.ts`)로 했다. rhwp 소스는 `v0.8.7` 태그로 읽었다(`src/document_core/commands/paragraph_block/import/resources.rs`·`resources/styles.rs`, `src/renderer/layout.rs` `NumberingState`, `src/wasm_api.rs` `delete_style`).

## 결정

**rhwp 기준 GO(보정 넷 + 넣은 문단 다시 배치), 한글 프로그램 확인 대기.** `importParagraphBlock` 으로 서식째 복사하고, rhwp 동작이 스펙과 다른 곳만 어댑터가 바로잡는다(ADR 002 원칙 그대로). 사용자가 `~/Downloads/docbridge-copy-check/` 파일을 한글에서 열어 경고가 없고 번호·스타일·표·그림이 맞으면 이 ADR 을 accepted 로 바꾼다. 경고가 나면 "NO-GO 일 때" 절로 간다.

1. **원본 핸들 = HWPX 바이트를 열어 HWP 로 한 번 바꾼 핸들, 거부되면 HWPX 그대로 연 핸들.** 원본 탭은 스펙대로 HWPX 바이트(`exportHwpx`)를 보내고, 대상 탭이 `new HwpDocument(new HwpDocument(hwpx).exportHwp())` 로 연다. HWPX 그대로 연 핸들은 번호 정의(`paraHead`)·누름틀 문단을 거부한다(근거 테스트). 옮기기(ADR 002 `DEFAULT_COPIES`)와 같은 순서·같은 이유다.
2. **dryRun → 실행.** 거부되면 대상은 그대로 두고 문단마다 이유를 모은다(`moveRejectReason` 재사용 — 각주·미주·머리말·꼬리말·감추기·책갈피·하이퍼링크 등). rhwp 는 **블록째 거부**하므로 "개체 일부를 빼고 가져와 warnings 로 알림" 은 할 수 없다 → 스펙을 "옮기기와 같이 거부하고 이유를 알린다" 로 바꾼다.
3. **번호 보정.** rhwp 는 번호 정의를 "내용이 모두 같을 때만" 대상 것으로 쓰는데, HWP 로 바꾼 핸들은 같은 공문끼리도 값이 달라 늘 새 정의를 더한다. rhwp 는 번호를 **번호 정의 id 마다 따로** 세므로(`NumberingState`) 가져온 문단이 "1." 부터 다시 시작하고 대상 번호도 끊긴다. 그래서 가져온 문단마다:
   - 자동 번호(`headType: Number`)이고 새로 더해진 정의면, 대상에 `levelFormats` 가 같은 정의가 있을 때 그 정의로 `applyParaFormat({numberingId})` → 대상 위치를 따라 이어진다("1. 관련 / 2. 회신 / 3. 하반기 / 4. 회신"). 같은 모양 정의가 여럿이면 **넣는 자리 바로 앞 문단의 정의**(그 문단이 자동 번호일 때), 아니면 첫 정의(#64, PR #70 리뷰). 없으면 새 번호 목록(1부터) 그대로.
   - 개요(`headType: Outline`)면 rhwp 가 원본 구역 개요 번호를 복제해 붙인 것이므로 `numberingId: 0`(대상 구역 개요 번호)으로 → 대상 개요를 따라 "2." 가 되고 뒤 개요도 다시 매겨진다.
4. **스타일 보정.** rhwp 는 스타일도 "이름·모양·다음 스타일까지 모두 같을 때만" 대상 것을 쓰고, 아니면 원본 스타일을 대상에 **더한다**(그 스타일이 쓰는 글자·문단 모양도 더한다). 그래서 대상에 "바탕글" 이 있어도 "바탕글" 이 하나 더 생긴다. 가져온 문단(과 그 안 표의 칸 문단)의 스타일이 새로 더해진 것이고 대상에 **같은 이름** 이 있으면 그 스타일로 `applyStyle`/`applyCellStyle` 한다(rhwp 동작: 스타일 모양이던 글자·문단 모양만 대상 스타일 모양이 되고 직접 서식은 남는다 — Word 의 "대상 스타일 사용"). 대상에 같은 이름이 **없으면** rhwp 가 더한 스타일을 그대로 둔다(원본 이름·모양 그대로 — 스펙의 "바탕글 + 원본 모양" 대신, 아래 열린 질문 결론).
5. **복제 스타일 정리.** 보정 뒤 아무도 쓰지 않는 복제 스타일(대상에 같은 이름이 있는 새 스타일)은 큰 번호부터 `deleteStyle`. 대상의 원래 문단은 원래 번호(더한 것보다 작다)만 쓰므로 "아무도 쓰지 않음" 은 넣은 문단(과 그 칸 문단)만 보고 정한다(#64 — 대상 문서 전체를 훑지 않는다). 지우기 전에 더한 스타일(복제가 아닌 것)의 다음 스타일이 복제를 가리키면 대상의 같은 이름 스타일로 돌린다 — rhwp 는 다음 스타일도 복제로 다시 매기고, `deleteStyle` 은 지운 스타일을 가리키던 다음 스타일을 바탕글로 바꾼다(#64 프로브: "다음은 개요" → "개요 1" 이 바탕글이 됨). 이름 바꾸기(`updateStyle`)가 실패하면 같은 이름이 둘 남으므로 던진다(편집 공용 경로가 스냅샷으로 되돌린다). rhwp `deleteStyle` 은 본문 문단의 스타일 번호만 당기고 **표 칸 문단은 손대지 않는다**(근거 테스트). 그래서 넣은 칸 문단이 지울 스타일보다 뒤 번호(남기는 새 스타일)를 쓰면 지우지 않고, 한글이 붙여 넣을 때처럼 **"이름 사본N"** 으로 바꾼다(`updateStyle`). 같은 이름 스타일이 둘 남지 않는다.

6. **넣은 문단 다시 배치(#85).** `importParagraphBlock` 은 원본 문서 폭으로 계산된 줄 배치(`<hp:lineseg>`)를 그대로 가져오고 다시 배치하지 않는다. 그래서 본문 폭이 넓은 문서에서 한 줄이던 문단을 좁은 문서에 넣으면 한 줄로 남아, 초록 표시·`highlight` 상자·더블클릭 자리가 첫 줄 일부만 잡히고 저장 파일에도 원본 폭(`horzsize`) 줄 배치가 남는다(한컴이 저장된 줄 배치를 믿으면 글자가 겹칠 위험). 번호·스타일 보정(`applyParaFormat`·`applyStyle`)을 거친 문단은 그때 다시 배치돼 맞았고, 보정을 거치지 않는 문단(대상에 없는 스타일 등 — v0.2 QA 의 공고문 → 제안서)만 틀렸다. 보정 뒤 넣은 문단마다 **문단 모양을 같은 번호로 다시 건다**(`setParaShapeId(같은 id)` — 편집하면 맞아지는 경로처럼 그 문단만 다시 배치). `reflowLinesegs()` 는 줄 배치가 비었거나 높이 0 인 문단만 다시 계산해서 이 경우를 고치지 못한다(프로브: 0문단). 표 칸 문단은 표가 칸 폭째 들어와 폭이 같아 보지 않는다.

7. **열 때 줄 배치 다시 계산(#89).** 다시 배치한 넣은 문단도 rhwp 가 저장할 때 "합성한 줄 배치" 로 보고 `linesegarray` 를 빼는 일이 있다(rhwp #1380, 좁은 테스트 문서에서 생김). 한컴은 열 때 다시 계산해 괜찮지만, rhwp 는 줄 배치가 빈 문단을 한 줄로 둬서 그 파일을 docbridge 로 다시 열면 초록 표시·`highlight` 상자·더블클릭 자리가 첫 줄 일부만 잡혔다. 다른 도구가 줄 배치 없이 저장한 파일도 같다. 그래서 문서를 여는 공용 함수(`src/core/open-document.ts` `openHwpDocument` — 뷰어 `load_document`(새로고침해 다시 띄울 때 포함)·`create_document` 양식·Node 테스트 뷰어)가 줄 배치가 빈 본문 문단(`getValidationWarnings` 의 `LinesegArrayEmpty`, 칸 문단 제외)이 있을 때만 **`reflowLinesegs()` 를 한 번** 부른다. 그 전에 **구역 첫 문단이 그 목록에 있으면 그 문단만 문단 모양을 같은 번호로 다시 건다**: 구역 정의가 든 첫 문단은 rhwp 가 저장한 HWPX 에서 자주 줄 배치가 비는데(fixture notice·application·report), 그대로 `reflowLinesegs()` 를 부르면 뒤 문단의 `vertpos` 가 한 줄씩 밀린 채 저장된다(fixture 5개 중 3개, 화면은 같다 — 근거 테스트). 이렇게 하면 fixture 5개의 블록·블록 사각형·HWPX 저장 바이트가 그냥 연 것과 같다. 구역이 둘이고 구역마다 머리말·꼬리말이 있는 문서(fixture `sections.hwpx`, #80)에서 줄 배치를 모두 빼고 열어도 두 구역 첫 문단까지 다시 배치돼 블록·블록 사각형이 줄 배치가 있는 파일과 같고, 머리말·꼬리말 문단은 `LinesegArrayEmpty` 목록에 나오지 않아 손대지 않는다(근거 테스트). 줄 배치가 빈 문단마다 문단 모양을 다시 거는 방법(6과 같은 방법)도 저장 결과는 같았지만 부를 때마다 구역을 다시 조판해 15쪽 297문단에 5초가 걸려 쓰지 않는다(아래 측정).

`copy_blocks` 구현(#64)은 `copyParagraphs` 를 편집 종류(`edit-operations.ts` `copy_blocks`)로 감쌌다. 원본 탭은 저장과 같은 `export_hwpx`(내보내 다시 열어 블록이 같은지 확인한 바이트 — 문단 위치를 믿을 수 있다)로 바이트를 내고, 서버(`src/server/copy-tool.ts`)가 원본 범위(`move-plan.ts` `planCopySource`)와 함께 대상 탭 편집에 싣는다. 넣은 문단마다 원본 블록 꼬리표(문단 글자·표·누름틀)를 `changes.inserted[].parts` 로 돌려주고, 편집 공용 경로가 넣은 문단의 실제 블록과 같은지 확인한다(다르면 되돌림). 처음 계획대로 스냅샷 하나로 넣은 문단·더한 스타일·번호 정의·그림까지 되돌아간다(undo, 보정 중 예외, 넣은 블록 불일치 모두 — 근거 테스트). 원본 범위·대상 기준 규칙은 `move_blocks`·`insert_paragraph` 와 같다(구역 첫 문단과 그 앞자리 거부).

근거 테스트 `글자 크기·굵게·정렬은 남지만 번호·표·그림·스타일을 잃는다`, 한글 확인 파일 06. 표·번호가 빠지면 스펙 목표("공고문의 신청 자격을 신청서 표에", "작년 보고서 3장을")를 못 한다 → 쓰지 않는다. `copySelection`/`pasteInternal`(내부 클립보드)은 WASM 인스턴스 안의 클립보드라 탭이 다르면 쓸 수 없다.

### 큰 대상 문서 (#64, PR #70 리뷰 후속)

원본 = 기술 검증 원본(공문 + 그림·스타일 문단)의 번호 문단부터 끝까지 13문단(표·그림 포함), 대상 앞 2번째 문단 앞에 `copyParagraphs`. 원본 핸들 만들기(작은 원본) 포함, 세 번 잰 값. Node 24, Apple M3 Pro. 대상은 rhwp 레포 `samples/` 문서라 측정 스크립트는 레포에 넣지 않았다(호출마다 시간을 재는 감싸기).

| 대상 | 쪽·문단 | 고치기 전(#62) ms | 고친 뒤 ms | 고친 뒤 단계별 |
|---|---|---|---|---|
| 행정업무운영 편람 | 383쪽, 2,618문단 | 261 / 224 / 226 | 232 / 218 / 219 | `importParagraphBlock` 49ms×2(dryRun·실행), `applyStyle` 78ms×11, `applyCellStyle` 65ms×9, `getControls` 15ms×1, `getStyleAt` 0ms×26(전: 2,644번 1ms), `getStyleList` ×4(전: ×25) |
| 기부·답례품 양식 | 31쪽, 256문단 | 219 / 217 / 215 | 217 / 218 / 216 | `applyStyle` 107ms×12, `applyCellStyle` 79ms×9, 나머지 15ms 안 |

- 문서 전체 훑기(`getStyleAt` 문단마다)와 문단마다 스타일 목록 다시 읽기는 383쪽에서도 몇 ms 라 시간은 거의 같다. 고친 것은 호출 수가 대상 크기에 비례하지 않게 한 것(테스트 `보정은 넣은 문단만 본다`가 호출 수를 고정)
- 시간 대부분은 `applyStyle`·`applyCellStyle` 이 문단마다 구역을 다시 조판하는 것이다. 13문단 0.22초라 REQUEST_TIMEOUT(30초)·2초 기준 안이다. 수백 문단을 한 번에 복사하면 늘어난다 — 그때 스타일 보정을 문단 묶음으로 하는 API(rhwp)를 본다
- 원본이 큰 문서면 원본 핸들 만들기(383쪽 1.2초)가 더해진다(위 "로컬 한컴 문서")

## 열린 질문 결론 (SPEC-007 에 반영)

| 질문 | 결론 | 근거 |
|---|---|---|
| 문서 사이 복사가 rhwp 공개 API 로 서식째 되는지 | **된다(GO).** `importParagraphBlock` 이 글자·문단 모양·표·그림·누름틀을 대상 정의로 다시 매겨 가져온다. 번호·스타일만 위 보정 넷이 필요하다. 각주·미주·머리말·꼬리말·감추기 등이 든 문단은 블록째 거부(옮기기와 같은 목록) | 위 표, 로컬 한컴 문서 6개 저장 검증 통과 |
| (함께 정함) 대상에 같은 스타일 이름이 없을 때 | **원본 스타일을 대상에 더한다**(이름·모양 그대로). 스펙 초안의 "바탕글 + 원본 모양(직접 서식)" 은 칸 문단까지 바탕글로 돌릴 방법이 없고(`deleteStyle` 이 칸을 고치지 않고, `applyCellStyle` 은 모양을 덮는다), 원본 스타일 이름이 남는 편이 사용자가 한글에서 고치기 쉽다 | `AC-6 …`, `rhwp deleteStyle 은…` |
| (함께 정함) 대상에 같은 이름 스타일이 있을 때 | **대상 스타일을 쓴다**: 스타일 모양이던 글자·문단은 대상 스타일 모양, 직접 서식(굵게·18pt 등)은 원본 그대로 | `같은 이름 스타일의 모양이 대상과 다르면…` |
| (함께 정함) 옮기지 못한 개체 `warnings` | **없앤다.** rhwp 는 개체 일부만 빼고 가져오지 않는다. 거부 이유를 문단마다 알린다(`move_blocks` 와 같은 문구) | `각주가 든 문단은 블록째 거부…` |

"탭 대신 한 탭 안 문서 목록" 질문은 이 검증 범위 밖(뷰어 화면 결정)이라 열어 둔다.

## NO-GO 일 때 (한글에서 경고가 나면)

우회해서 GO 로 만들지 않고 결과를 이 ADR 과 스펙에 남긴다.

1. **00-원본도 경고** → 원본 만들기(그림 넣기·`createStyle`) 문제. ADR 003 확인 결과와 비교한다.
2. **05(보정 없음)는 괜찮고 01~04 만 경고** → 보정(`deleteStyle`·`applyStyle`·`applyParaFormat`) 문제. 보정을 하나씩 빼고 다시 만들어 가른다(스크립트에 보정 끄기를 더한다).
3. **01·04·05 만 경고, 02·03 은 괜찮음** → 그림·표·사용자 스타일 가져오기 문제. 그림 문단·스타일 문단을 뺀 범위로 가른다.
4. **쓰이지 않는 정의(복제 번호 정의·모양)가 원인** → 공개 API 로 지울 수 없다. 대안: (a) 복사 뒤 문서를 HWPX 로 내보내 다시 여는 정리, (b) rhwp 업스트림 이슈(가져오기 뒤 쓰이지 않는 정의 정리), (c) 같은 문서 안 복사만 허용(스펙 축소).
5. **번호·개요가 다르게 보임** → 한컴의 번호 계산과 rhwp 가 다른 것. 번호 정의 다시 가리키기(결정 3)를 다시 본다.

## 검토한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| `importParagraphBlock` + 보정 (선택) | 서식·표·그림·누름틀째, 대상 정의로 다시 매긴다. 공개 API 만 | HWP 왕복 비용(큰 문서 1초대), 보정 넷, 쓰이지 않는 복제 정의가 남는다 |
| `importParagraphBlock` 만 (보정 없음) | 코드가 없다 | "바탕글" 이 둘, 번호가 1부터 끊기고 개요가 따로 센다(근거 테스트, 확인 파일 05) |
| HWPX 그대로 연 원본만 | HWP 왕복이 없다, 같은 정의를 다시 쓴다 | 번호 문단·누름틀 문단을 거부한다 |
| `exportSelectionHtml` → `pasteHtml` | 거부가 없다 | 번호·표·그림·스타일을 잃는다(위 표) |
| 내부 클립보드(`copySelection` → `pasteInternal`) | 한 문서 안에서는 서식째 | 탭(WASM 인스턴스)마다 클립보드가 따로라 문서 사이에 못 쓴다 |
| 복제 스타일을 지우지 않고 모두 "사본N" 으로 | id 가 안 바뀌어 안전하다 | 복사할 때마다 "바탕글 사본1·2…" 가 쌓인다(HWP 왕복으로 늘 생긴다) |
| 대상에 없는 스타일을 바탕글 + 직접 서식으로 | 스펙 초안 그대로 | 칸 문단은 방법이 없고(위), 본문은 `deleteStyle` 로 되지만 원본 스타일 이름을 잃는다 |

## 결과

- 쉬워지는 것: `copy_blocks`(#64)는 서버가 원본 탭에 `export_hwpx`(이미 있는 저장 경로)로 바이트를 받아 대상 탭 편집 요청에 실어 보내고, 대상 탭은 `copyParagraphs` 를 편집 종류(`ParagraphChanges.inserted` = 넣은 문단들)로 감싼다. 거부 문구·범위 규칙은 `move_blocks` 것을 그대로 쓴다.
- 어려워지는 것: rhwp 의 가져오기 의미(내용으로 정의 맞추기, 번호 정의 id 별 세기, `deleteStyle` 이 칸을 안 고치는 것)가 바뀌면 보정이 틀어진다. `(근거)` 테스트가 지금 동작을 고정한다.
- 다시 볼 조건: 사용자 한글 확인 결과(위 NO-GO 절). rhwp 가 쓰이지 않는 정의 정리·칸 문단까지 고치는 `deleteStyle`·경로로 칸 스타일을 읽는 API 를 내면 이름 바꾸기·보정을 걷어낸다. 큰 문서 복사가 2초를 넘으면 원본 핸들 캐시(원본 탭의 편집 번호로 무효화)를 본다.
- 확인 못 한 것: 한글 프로그램에서 열기(사용자), **표 안 표**의 칸 문단 스타일(rhwp 에 경로로 칸 스타일을 읽는 API 가 없다 — 이런 칸이 복제 스타일을 쓰면 지운 뒤 바탕글이 된다, 모양은 그대로), 번호 정의를 `levelFormats` 로만 맞춘 것(`getNumberingList` 가 번호 모양(숫자·가나다)을 주지 않는다 — 형식 글자가 같고 모양이 다른 정의가 있으면 번호 모양이 바뀔 수 있다. 넣기 전후 번호 문자열 비교로 막는 일은 #64 에서 하지 않았다 — 실제 문서에서 본 적이 없어 남겨 둔다), 여러 구역 사이 복사(fixture 가 한 구역 — 요청 형식은 구역을 따로 받는다), 브라우저 안의 시간(Node 로만 — 같은 WASM).
