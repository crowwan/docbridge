# 002. 편집·되돌리기·HWPX 저장 방식

## 상황

SPEC-002(말로 고치기와 저장)의 기능 이슈(#19~#23)에 들어가기 전에, `@rhwp/core` 0.8.7 공개 API 로 다음이 스펙대로 되는지 확인해야 했다(#18).

- 같은 문서 안에서 이어진 문단 여러 개를 서식째 옮기기(`importParagraphBlock` + `deleteParagraph`), 자동 번호가 새 순서로 다시 매겨지는지, 거부되는 컨트롤, 사본 비용
- 글자·표 칸·누름틀 값 바꾸기에서 바뀐 자리 첫 글자의 글자 모양 유지, 새 문단의 기준 문단 모양
- 20단계 되돌리기(`saveSnapshot`/`restoreSnapshot`)와 블록 id 표 같이 되돌리기
- HWPX 내보내기 보고서(`exportHwpxWithReport`)와 다시 열어 비교하는 비용
- 블록 캐시를 서버에 둘지, 새로고침·저장 뒤 "마지막 파일"을 어떻게 할지(스펙 열린 질문 3개)
- 편집한 파일이 **한글 프로그램에서 경고 없이 열리는지** — rhwp 저장 파일이 한컴에서 "손상"·"변조"로 거부된 사례가 많다(조사 문서: #190, #7219, #1244, 저장·라운드트립 손상 73건)

근거 자료: `docs/research/rhwp-code-analysis.md` 2·5장, `docs/research/rhwp-issues-analysis.md`. 확인은 프로토타입 함수(`src/core/edits.ts`, `edit-history.ts`, `hwpx-export.ts`)와 테스트(`tests/edit-spike.test.ts`, 묶음 `SPEC-002 … (기술 검증)`)로 했다.

## 결정

**rhwp 기준 GO, 한글 프로그램 확인 대기.** 아래 방식으로 편집하고 저장한다. 사용자가 한글에서 `scripts/make-hwp-check.ts` 결과 파일을 열어 경고가 없으면 이 ADR 을 accepted 로 바꾼다. 경고가 나면 "NO-GO 일 때" 절로 간다.

1. **편집은 뷰어(rhwp)에서, rhwp 기본 동작이 스펙과 다른 곳만 어댑터(`src/core/edits.ts`)가 바로잡는다.** 포크·패치하지 않는다(ADR 001 원칙 그대로).
2. **옮기기** = HWP 사본 → 사본이 원본과 같은지 확인(구역 문단 수·옮길 문단 글자) → `importParagraphBlock` dryRun → 실행 → 원본 문단 지우기(인덱스 보정) → **옮긴 문단의 문단 모양 id 를 원래 값으로 되돌리기**(`setParaShapeId`, 번호는 원본 문서에서 읽는다). 사본을 못 만들거나 원본과 다르거나 거부되면 HWPX 사본으로 한 번 더 본다. 구역 첫 문단과 그 앞자리는 막는다.
3. **글자 바꾸기**(문단·칸·값이 있는 누름틀) = 바뀌는 자리 **첫 글자 바로 뒤에 새 글자를 넣고, 나머지 옛 글자와 첫 글자를 지운다.** rhwp `replaceText`·`setFieldValue` 는 쓰지 않는다(빈 누름틀만 `setFieldValue`).
4. **문단 넣기** = `insertParagraph` 뒤 기준 문단 모양으로 `setParaShapeId`, 글자 모양이 다르면 기준 글자 속성을 `applyCharFormat` 으로 건다(빈 문단은 자리 글자를 넣어 맞춘 뒤 지운다). 구역 첫 문단 앞에는 넣지 않는다.
5. **되돌리기** = 편집마다 `saveSnapshot` 하나 + 편집 전 블록 id 표 사본. 20칸을 넘으면 가장 옛 스냅샷을 `discardSnapshot`.
6. **저장** = `exportHwpxWithReport` → 바이트를 `new HwpDocument` 로 다시 열어 블록(위치·글자·번호·칸·누름틀 값)을 비교 → 같을 때만 쓴다. 다시 열지 못해도 예외가 아니라 검증 실패(`reopenError`). 손실 보고가 있으면 경고.
7. **블록 캐시는 서버에 두지 않는다.** 뷰어가 편집마다 블록을 다시 뽑아 들고, 서버는 지금처럼 도구마다 받는다.
8. **저장하면 저장 경로가 "마지막 파일"이 되고, 새로고침하면 마지막으로 저장한(없으면 연) 파일로 돌아간다.** 저장하지 않은 편집은 사라지고 알린다.

**거부되는 컨트롤(0.8.7 실제 확인).** dryRun 오류는 `렌더링 오류: paragraph block: source: paragraph block unsupported at [Paragraph(<범위 안 순서>), Control(n)…]: <이유>` 형식이고 **첫 거부 하나만** 알려준다. 그래서 거부되면 문단마다 다시 dryRun 해서 모두 모은다(`MoveRejection[]`, 이유는 한글 이름으로 바꾼다).

- **하이퍼링크는 옮겨진다.** rhwp 가 만드는 일반 하이퍼링크(누름틀 형식)는 거부되지 않았다(스펙 초안의 "하이퍼링크 거부"를 고친다).
- **사본 형식.** HWPX 사본은 HWPX 번호 정의(`raw_para_heads`)를 가져오지 못해 **번호 문단을 거부한다**(`Number(2): opaque HWPX paraHead import is not supported`). HWP 사본은 한컴 HWPX 의 **그리기 개체(gso)를 해석하지 못한 컨트롤 데이터로 바꿔 거부한다**(로컬 `real-hwpx-01.hwpx` 29번 문단). 그래서 HWP 사본을 먼저 쓰고, 거부되면 HWPX 사본으로 한 번 더 본다. 둘 다 거부되면 거부가 적은 쪽(같으면 HWPX 쪽, 컨트롤 이름이 남는다)을 돌려준다. 로컬 한컴 문서 4개에서 문단 하나씩 dryRun: HWP 사본 거부 1·2·20·3개, HWPX 사본 1·2·19·3개.
- **구역 첫 문단 앞으로 옮기기는 막는다.** 넣은 문단이 첫 문단이 되고 구역·단 정의(`secd`·`cold`)는 둘째 문단에 남는다. rhwp 는 다시 열지만 한글 파일 구조(구역 정의는 구역 첫 문단)와 달라 한컴에서 문제가 될 수 있다(근거 테스트). 첫 문단 자체도 위 표처럼 거부된다.
- **구역의 마지막 문단.** `deleteParagraph` 는 구역에 문단이 **하나만** 남을 때만 거부한다("구역의 마지막 문단은 삭제할 수 없습니다", 마지막 번째 문단은 지워진다). 옮기기는 사본을 먼저 넣고 원본을 지우므로 걸리지 않는다.
- 직접 입력한 번호("1.", "가.")는 그대로 옮겨지고 바뀌지 않는다(로컬 한컴 기안문 — 번호가 모두 글자다). AC-6 경고는 문단 앞 글자 패턴으로 #21 에서 정한다.

### 글자 바꾸기·칸·누름틀

- **rhwp `replaceText` 는 지우고 넣는데, 넣은 글자가 앞 글자 모양을 따른다.** "가나**다라**마바" 의 "다라" 를 바꾸면 굵기가 사라진다(근거 테스트). rhwp 의 넣기는 모두 앞 글자 모양을 물려준다(위치 0 이면 뒤 글자).
- **첫 글자 뒤에 넣고 지우기**: `insert(start+1, text)` → `remove(start+1+len(text), end-start-1)` → `remove(start, 1)`. 바뀐 글자가 첫 글자의 **글자 모양 id 그대로**를 받는다(`applyCharFormat` 로 다시 거는 방법은 같은 속성의 새 id 가 생겨서 쓰지 않았다). `바뀐 글자는 바뀌는 자리 첫 글자의 글자 모양을 따른다`.
- 빈 범위(넣기)는 앞 글자 모양. 빈 글자로 바꾸면 지우기.
- **줄바꿈은 받지 않는다.** `replaceText` 에 `\n` 을 주면 문단을 나누지 않고 문단 안 글자로 들어간다(문단 수 그대로). 한컴에서 어떻게 보일지 알 수 없어 거부한다 — 새 문단은 `insert_paragraph`.
- 글자 위치는 유니코드 글자 단위 그대로 넘긴다(`😀가𠀀나` 에서 2..3 → `😀가X나`).
- **표 칸**: 0.8.7 에는 일반 `replaceTextInCell` 이 없다(`replaceTextInCellDeferredPagination` 은 IME 조합용). `insertTextInCellByPath`/`deleteTextInCellByPath`(경로 `[{controlIndex,cellIndex,cellParaIndex}]`) 로 같은 방법을 쓴다. 칸 text 위치(`\n` 으로 이은 것)는 칸 안 문단·위치로 바꾸고, 여러 문단에 걸치면 `deleteRangeInCell` 로 지워 문단을 합친다.
- **누름틀**: `setFieldValue(ByName)` 도 값의 글자 모양을 버린다(근거 테스트). 값이 있으면 `getFieldList` 의 `startCharIdx` 기준으로 같은 방법(표 안 누름틀은 `location.path` 경로)을 쓰고 값이 기대와 같은지 다시 읽어 확인한다. 값이 비었으면 따를 글자가 없어 `setFieldValue(fieldId)`. **값 맨 앞·맨 뒤 자리는 누름틀 밖이다**(PR #24 리뷰: 넣으면 값이 안 바뀐다). 맨 뒤에 붙이면 마지막 두 글자를 "두 글자 + 글자" 로, 맨 앞이면 첫 글자를 "글자 + 첫 글자" 로 바꿔 넣는 자리를 값 안쪽으로 둔다. 한 글자 값은 안쪽 자리가 없어 값을 통째로 넣고 그 글자 속성을 다시 건다. 이름은 겹칠 수 있어(실제 기안문 `*검토1`·`검토1` 등) `ByName` 대신 `fieldId` 를 쓴다. #19 에서는 블록에 `fieldId` 를 넣지 않고, 서버가 보낸 위치의 "같은 문단 안 몇 번째 누름틀"(하이라이트와 같은 방법)로 `getFieldList` 에서 `fieldId` 를 고른다(`src/core/edit-operations.ts`).

### 문단 넣기

- `insertParagraph(sec, i)` 는 **i-1 문단**의 문단 모양·끝 글자 모양을 물려준다(Enter 와 같다). 뒤에 넣기(`i = 기준+1`)는 그대로 맞고, 앞에 넣기는 `setParaShapeId(기준 문단 모양)` 로 바로잡는다(근거 테스트). 글자를 넣은 뒤 기준 첫 글자와 속성이 다르면 `applyCharFormat(기준 글자 속성 JSON)`.
- `splitParagraph(기준, 0)` 로 앞에 넣는 방법은 쓰지 않는다: 위치 0 의 컨트롤(표·구역 정의)이 앞(새) 문단에 남는다.
- 번호 문단 앞에 넣으면 새 문단도 번호를 받아 번호가 다시 매겨진다("1. 새로 넣은 항목", "2. 관련").
- **구역 첫 문단 앞에는 넣지 않는다**(PR #24 리뷰). rhwp 는 구역·단 정의를 둘째 문단에 남기고, HWPX 로 저장해 다시 열면 구역 정의가 둘(0번·1번 문단)이 된다(근거 테스트).
- 빈 문단을 앞에 넣으면 글자 모양 보정이 없어 앞 문단 끝 글자 모양이 남았다. 자리 글자 하나를 넣어 맞춘 뒤 지운다(빈 문단이 그 글자 모양을 남긴다).

### 문단 지우기 (#20)

- `deleteParagraph(구역, i)` 는 문단을 통째로 지운다. 표가 든 문단이면 표째, 누름틀이 든 문단이면 누름틀째 지워진다. 구역에 문단이 **하나만** 남으면 "구역의 마지막 문단은 삭제할 수 없습니다".
- **구역 첫 문단을 지우면 그 안의 구역·단 정의(`secd`·`cold`)도 같이 지운다**(`getControls` 에서 사라진다). HWPX 로 내보내 다시 열면 정의가 다시 생기지만 편집 중 문서에는 정의가 없다. 그래서 `delete_blocks` 는 구역 첫 문단을 지우지 않는다(옮기기·넣기와 같은 이유). 첫 문단을 지우지 않으므로 구역이 비는 삭제도 생기지 않는다.
- `deleteTableControl(구역, 문단, 컨트롤)` 은 표만 지우고 문단(글자)은 남긴다. 글자 없는 표 문단이면 빈 문단이 남아 빈 줄이 된다. 그래서 표 블록을 지울 때 그 문단에 다른 블록(문단 글자·다른 표·누름틀)이 없으면 `deleteParagraph`, 있으면 `deleteTableControl`. 같은 문단 뒤 표들의 컨트롤 번호는 하나씩 당겨진다(id 표 `tableDeleted`).
- **`deleteTableControl` 은 같은 문단의 누름틀을 잃는다**(표 안·표 밖 모두, `getFieldList` 에서 사라지고 HWPX 로 내보내 다시 열어도 없다, 근거 테스트). 그래서 누름틀이 든 문단에서 표만 지우는 것은 거부한다. 지울 표 안 누름틀만 있으면 표와 같이 사라지는 것이라 "다른 블록"으로 세지 않고 문단째 지운다. 표 안·문단 직속은 `getFieldList` 의 `location.path` 로 가른다(PR #29 리뷰).
- **문단째 지울 문단에 블록이 아닌 개체가 있으면 거부한다**(글자 있는 문단도). `getControls` 의 `ctrlId` 로 종류를 본다: 표(`tbl`, 블록)와 문단 글자와 같이 사라져도 되는 보이지 않는 인라인 컨트롤(책갈피 `bokm`, 새 번호 `nwno`, 번호 넣기 `atno`, 찾아보기 표시 `idxm`, 누름틀·하이퍼링크 같은 필드 `''`·`%…`)만 허용하고, 구역·단 정의, 머리말·꼬리말, 각주·미주, 그림·도형(`gso`), 수식(`eqed`), 쪽 번호 위치, 감추기 등은 이유(`userDesc`)와 함께 거부한다. 쪽 번호 위치·감추기는 보이지 않지만 지우면 쪽 모양이 조용히 바뀌어 거부 쪽에 둔다. `getControls` 는 (목록, 문단)으로 주므로 구역마다 본문 목록 번호를 구역 정의(첫 문단 `secd`) 순서로 알아내고, 문단 컨트롤 수가 `getControlTextPositions` 와 다르면 확인하지 못했다고 거부한다(여러 구역 문서는 fixture 가 없어 확인 못 함).
- **id 표는 뷰어가 실제로 한 일로 옮긴다**(PR #29 리뷰). 뷰어가 무엇을 지울지(문단째·표만) 정하고 편집 결과에 `ParagraphChanges`(`src/core/paragraph-changes.ts`: 표만 지운 자리·통째로 지운 문단은 편집 전 위치, 넣은 문단은 편집 뒤 위치)를 실어 보낸다. 서버는 이것대로 `tableDeleted` → `paragraphDeleted`(뒤에서부터) → `paragraphInserted`(앞에서부터)를 하고, 지운 id·새 id 도 여기서 나온다. 서버가 따로 계획하면 둘이 어긋날 때 id 가 조용히 엉뚱한 블록을 가리킨다. 서버는 블록 위치만으로 아는 거부(누름틀 블록·구역 첫 문단)만 뷰어에 보내기 전에 한다.
- **`relocate(changes)`** = 편집 전 문단 위치 → 편집 뒤 위치. 통째로 지운 문단은 `undefined`, 그 밖은 앞에서 지운 문단 수만큼 당긴 뒤 넣은 문단 자리(편집 뒤 위치, 오름차순)마다 그 자리 이상이면 하나씩 민다. 표만 지운 자리는 문단 위치가 그대로다. 뷰어는 이것으로 "블록으로 남길 빈 문단"(편집으로 비운 문단 블록) 위치를 옮기고, 서버 id 표 연산이 같은 결과를 낸다. 문단을 옮기는 편집(#21)도 같은 장치로 합친다. 여러 블록을 지워도 편집 하나(스냅샷 하나)다.
- 되돌리기는 스냅샷이 문서를 편집 전 그대로 돌려놓으므로, 뷰어는 블록을 다시 뽑지 않고 편집 전에 뽑아 둔 블록 목록을 같이 쌓았다가 돌려놓는다(다시 뽑으면 넣기·지우기 뒤 위치로 "블록으로 남길 빈 문단"을 골라 엉뚱한 빈 문단이 블록이 된다).

### 되돌리기

- `saveSnapshot()` 은 문서 전체를 복제한다. `snapshotCapacity()` = 100(rhwp studio 예산). 우리는 20칸만 쓰고 넘치면 `discardSnapshot`. 기록 하나는 문서 핸들 하나에 묶이고, 새 문서·새로고침 때 `dispose()` 로 닫는다(버린 편집 수를 돌려줌).
- 블록 id 표는 편집 전 사본(`BlockIdTable.clone()`)을 스냅샷과 같은 칸에 둔다. `undo(n)` 은 가장 옛 칸 스냅샷으로 `restoreSnapshot` 하고 그 칸의 id 표를 돌려준다(`EditHistory`). 거부된 편집(옮기기 거부)은 기록하지 않는다.
- 실제 구성(#19): 스냅샷은 문서와 같이 뷰어에, id 표 사본은 서버에 있다. 서버가 `{이름, id 표 사본}` 스택(`src/server/edit-log.ts` `EditLog`)을, 뷰어가 같은 순서의 스냅샷 스택(`src/core/document-editor.ts` `DocumentEditor` 안 `EditHistory`)을 들고 `undo` 요청 하나로 둘 다 꺼낸다. 서버는 편집·되돌리기를 문서 열기와 같은 줄에 세워 하나씩 보내 두 스택 순서가 어긋나지 않게 한다. 새 문서 때 둘 다 비운다(새로고침은 #22). 두 기록이 같은지는 요청마다 서버가 편집 순번(적용 − 되돌림, 상한 없이)을 실어 보내 뷰어가 확인한다. 다르면(앞 요청 타임아웃 등) 아무것도 하지 않고 어긋남 오류. 뷰어는 다시 그리기·표시까지 성공해야 스냅샷을 기록에 넣는다(PR #26 리뷰). "저장하지 않은 편집" 수는 되돌리기 칸(20)과 따로, 연 뒤 지나온 상태 줄과 저장한 때 줄이 갈라진 길이로 센다(20개를 넘게 고치거나 저장한 뒤 되돌려도 맞다).

### HWPX 저장 검증

- `exportHwpxWithReport()` → `DocumentExport`: `contentLoss()` JSON = `{schemaVersion:1, outputFormat:"hwpx", count, losses:[{code, subject, path, reason, resourceId?}]}`(`code`: `binaryContentEmptied`·`controlOmitted`·`metadataReduced`, `reason`: `resourceReadFailedOrLimitExceeded`·`storedCompressionMismatch`·`rawPassthroughUnavailable`·`unsupportedByOutputFormat` — `src/serializer/content_loss.rs`), `takeBytes()` 는 한 번만. 측정한 11개 문서 모두 손실 0건.
- 비교는 블록의 위치(구역·문단·컨트롤)·글자·번호·개요 수준·칸·누름틀 값(쪽은 조판 결과라 뺀다, `blockContent`). 편집한 fixture 3개와 로컬 한컴 문서 모두 다른 블록 0개. 위치까지 같으므로 **저장한 파일을 다시 열면 같은 블록 id 표를 그대로 쓸 수 있다**.
- HWPX 구조 확인(스크래치, 결과물 8개): `mimetype` 이 첫 항목·무압축, 모든 XML 이 올바름, `paraPrIDRef`·`charPrIDRef` 가 모두 header 에 있음.

## 열린 질문 결론 (SPEC-002 에 반영)

| 질문 | 결론 | 근거 |
|---|---|---|
| 블록 캐시를 서버에 둘지 | **두지 않는다.** 뷰어가 편집이 끝날 때마다 블록을 다시 뽑아 들고(지금 `currentBlocks`), 서버는 지금처럼 도구마다 뷰어에서 받는다. 편집 결과는 바뀐 블록 id(표시용)만 돌려준다 | 블록 다시 뽑기 74쪽 54ms, JSON 387KB(127.0.0.1 WebSocket). "바뀐 블록만 받아 갱신"은 번호가 다시 매겨지는 편집(옮기기·넣기·지우기)에서 바뀐 블록이 편집 대상 밖까지 번져 계산이 따로 필요하고 틀리기 쉽다. 블록 뽑기가 200ms 를 넘거나 JSON 이 2MB 를 넘는 문서가 나오면 다시 본다 |
| 저장 후 "마지막 파일"을 저장 경로로 바꿀지 | **바꾼다.** 저장하면 저장 경로가 마지막 파일이 되고, 그때의 블록 id 표를 "기준 표"로 떠 둔다 | 저장 검증이 위치까지 같은 블록을 확인하므로 저장한 파일을 다시 열면 id 표를 그대로 쓸 수 있다. 바꾸지 않으면 새로고침 때 원본을 다시 읽어 저장한 편집까지 화면에서 사라진다 |
| 새로고침하면 저장하지 않은 편집이 사라지는 문제 | **사라지게 두고 알린다.** 새로고침하면 마지막 파일(저장했으면 저장 파일, 아니면 연 파일)을 다시 읽고, 서버는 id 표를 기준 표로 되돌리고 되돌리기 기록을 비운다. 다음 도구 결과에 "뷰어를 새로고침해서 저장하지 않은 편집 <n>개가 사라졌습니다." 를 붙인다. 뷰어는 저장하지 않은 편집이 있으면 탭을 닫거나 새로고침할 때 브라우저 확인 창(`beforeunload`)을 띄운다 | 뷰어 메모리 문서를 미리 서버에 보내 두려면 편집마다 내보내기가 필요하다(74쪽 `exportHwp` 246ms + 4.5MB 전송). 다시 띄운 문서는 사용자 파일이 아니라 rhwp 가 다시 쓴 파일이 되고, 되돌리기 기록(스냅샷)은 어차피 살릴 수 없다. 편집은 채팅으로 다시 시킬 수 있다 |

## NO-GO 일 때 (한글에서 경고가 나면)

사용자 확인 결과에 따라 이렇게 나눈다. 우회해서 GO 로 만들지 않고 결과를 이 ADR 과 스펙에 남긴다.

1. **기준 파일(편집 없이 rhwp HWPX 저장)도 경고** → rhwp HWPX 직렬화 자체 문제. 편집 방식과 무관하다. 대안: (a) **원본 ZIP 최소 패치** — 원본 HWPX 를 그대로 두고 `Contents/section*.xml` 의 바뀐 문단 XML 만 갈아 끼운다(header 는 원본 그대로, 새 정의가 필요한 편집은 막음). 원본이 `.hwp` 면 이 길이 없다. (b) rhwp 업스트림에 재현 파일로 이슈(메인테이너 응답 중앙값 29.5시간, 조사 문서). (c) v0.1 저장 범위를 "원본이 HWPX 인 문서의 글자 바꾸기·칸 채우기"로 줄인다.
2. **기준은 괜찮고 편집한 파일만 경고** → 편집 방식 문제. 파일마다 바꾼 것이 달라(README.txt) 어느 편집인지 가른다. 옮기기(복제된 정의가 남음)가 원인이면 옮긴 뒤 header 의 쓰이지 않는 정의를 없애는 방법이 공개 API 에 없으므로 (a) 원본 ZIP 패치, 또는 옮기기를 "글자만 옮기기(넣기+지우기)"로 바꾸는 안을 비교한다. 바꾸기·칸·누름틀이 원인이면 rhwp 이슈로.
3. **번호·글자가 다르게 보임** → 한컴의 번호 계산이 rhwp 와 다른 것. 옮긴 문단의 번호 시작 설정(`numberingRestartMode`)을 다시 본다.

## 검토한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| `importParagraphBlock` + 문단 모양 되돌리기 (선택) | 서식·표·누름틀째 옮긴다. 공개 API 만 | 사본 비용, 쓰이지 않는 복제 정의가 남는다, 번호 정의 복제를 되돌리는 보정이 필요 |
| `copySelection` + `pasteInternal` | 사본이 필요 없다 | 첫 문단이 도착 문단의 문단 모양을 받는다(조사 문서 2-2) — 번호 종류·들여쓰기가 바뀐다 |
| `applyTemplateOperation`(repeat) | 같은 문서 안 복제 | 템플릿 채우기 계약(`records` 수 = `count`)이라 옮기기에 맞지 않는다 |
| 글자만 옮기기(insert + delete) | 거부 컨트롤이 없다 | 표·누름틀·글자 모양을 잃는다. 스펙의 "거부 시 안내" 대안으로만 |
| `replaceText` / `setFieldValue` 그대로 | 코드가 없다 | 앞 글자 모양을 따라 굵게·색 등이 사라진다(근거 테스트) |
| 바꾼 뒤 `applyCharFormat` 으로 모양 다시 걸기 | 넣는 위치 계산이 없다 | 같은 속성의 새 글자 모양 id 가 계속 생긴다 |
| 사본을 HWPX 로만 | 한컴 그리기 개체를 받는다 | 번호 문단을 거부한다 |
| 새로고침 대비로 편집마다 문서를 서버에 보내기 | 새로고침해도 편집이 남는다 | 편집마다 내보내기·전송(74쪽 246ms·4.5MB), 다시 띄운 문서가 rhwp 재직렬화본 |
| 서버 블록 캐시(바뀐 블록만 갱신) | 도구 호출마다 전송이 준다 | 번호 재계산 범위 계산이 필요하고 틀리기 쉽다. 지금 크기에선 이득이 작다 |

## 결과

- 쉬워지는 것: #19~#22 는 `src/core/edits.ts`·`edit-history.ts`·`hwpx-export.ts` 를 뷰어 요청으로 감싸고, 서버는 id 표(`paragraphInserted`·`paragraphDeleted`·`paragraphsMoved`·`clone`)와 기준 표만 다룬다.
- 어려워지는 것: rhwp 의 넣기·복제 의미가 바뀌면(앞 글자 모양 상속, 번호 정의 복제) 어댑터 보정이 틀어진다. `(근거)` 테스트들이 rhwp 의 지금 동작을 고정해 두므로 버전을 올릴 때 이것이 먼저 깨진다.
- 다시 볼 조건: 사용자 한글 확인 결과(위 NO-GO 절), rhwp 가 같은 문서 옮기기 API(`moveParagraphBlock` 등)나 일반 칸 바꾸기 API 를 내면 걷어낸다. 블록 뽑기 200ms·JSON 2MB 를 넘는 문서가 나오면 블록 캐시를 다시 본다.
- 확인 못 한 것: 한글 프로그램에서 열기(사용자), 브라우저(Chromium) 안에서의 편집 시간(Node 로만 쟀다 — 같은 WASM 이라 비슷할 것으로 본다), 여러 구역 문서의 구역 사이 옮기기(스펙이 같은 구역만 다룬다면 막는다, #21).
